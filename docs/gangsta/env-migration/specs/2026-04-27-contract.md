# Contract: Extract Hardcoded Parameters to Environment Variables

## Objective
Move all hardcoded configuration parameters — credentials, secrets, API endpoints, Ollama settings, and other tunables — into environment variables. Update `docker-compose.yml` and `Dockerfile` to consume these variables via `.env` files. This improves security (no secrets in source), portability (one config per deployment), and operational flexibility (runtime overrides without rebuilds).

## Requirements

### Functional Requirements

**FR-001 — Admin credentials configurable via env**
The default admin username and password, currently hardcoded in `backend/db/seed.ts`, must be sourced from `ADMIN_USERNAME` and `ADMIN_PASSWORD` environment variables. The existing values (`admin` / `admin`) remain as fallbacks so existing dev/test workflows are not broken.

**FR-002 — JWT secret must be env-provided in production**
The JWT signing secret in `backend/routes/auth.ts` must read from `JWT_SECRET`. If `NODE_ENV=production` and `JWT_SECRET` is missing, the server must refuse to start (throw on boot). A development-only fallback (`money-tracker-secret-key`) is permitted when `NODE_ENV` is `development` or `test`.

**FR-003 — Ollama host and model fully env-driven**
In `backend/services/ocr.ts`, both the Ollama base URL (`OLLAMA_HOST`) and model name (`OLLAMA_MODEL`) must be sourced exclusively from environment variables. The current hardcoded defaults (`http://localhost:11434` and `qwen3-vl:235b-cloud`) must be removed from source code; they may remain as Docker Compose defaults only.

**FR-004 — Database path configurable**
The SQLite database file path in `backend/db/index.ts` must be overridable via `DB_PATH`. Default remains `import.meta.dir + "/data.sqlite"`.

**FR-005 — External rate API URL configurable**
The hardcoded Fawaz API URL in `backend/services/rateFetcher.ts` must be overridable via `RATE_API_URL`. Default remains the existing CDN URL.

**FR-006 — Docker Compose uses `.env` file and removes inline secrets**
`docker-compose.yml` must replace its hardcoded `environment:` map with `env_file: [.env]` (or a mix, keeping `NODE_ENV` and `PORT` inline if desired). All tunable values (Ollama host/model, JWT secret, admin credentials, DB path) must be sourced from the `.env` file.

**FR-007 — Document all variables in `.env.example`**
A `.env.example` file must be created at repo root listing every supported variable, its purpose, and its default value. It must NOT contain real secrets.

**FR-008 — Static dir remains env-aware**
`STATIC_DIR` is already read from `process.env.STATIC_DIR` with a fallback; this behavior is preserved unchanged.

### Non-Functional Requirements

**NFR-001 — Backward compatibility**
All changes must keep the application runnable without an `.env` file in local development (defaults work). Docker Compose must still work with `docker compose up` after a user copies `.env.example` to `.env`.

**NFR-002 — Test stability**
The existing `backend/tests/api.test.ts` must pass unchanged after the migration. The test harness sets `NODE_ENV=test`, which must trigger dev-level fallbacks.

**NFR-003 — No secret leakage in Docker layers**
No `.env` file containing real secrets must be copied into the Docker image. The `.dockerignore` already ignores `.env` / `.env.*`; this must remain enforced.

**NFR-004 — Fail-fast on missing required production vars**
If a required environment variable is absent in production, the application must exit during startup with a clear error message, not fail lazily at runtime.

## Architectural Decisions

1. **No central config module** — Environment variables are read at the point of use (`process.env.VAR || default`). A central module adds indirection without benefit for a small backend. If the number of variables grows past ~15, we will revisit.

2. **Fail-fast in production only** — We do not want to break local `bun run dev` workflows. Production Docker Compose will set `NODE_ENV=production`, triggering strict checks.

3. **`.env.example` as living documentation** — Rather than a README section, the example file is the canonical reference. It is tracked in Git; `.env` is gitignored.

## Grilling Conclusions

### Key Decisions
- Keep dev fallbacks for `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `DB_PATH`, `RATE_API_URL` so `bun test` and `bun run dev` work out-of-the-box.
- Remove hardcoded defaults from `OLLAMA_HOST` and `OLLAMA_MODEL` in source; these are infrastructure concerns, and silent fallback to localhost is confusing in Docker.

### Rejected Alternatives
- **Central `config.ts` module**: Rejected — over-engineering for ~7 variables, adds unnecessary abstraction.
- **Zod schema validation for env vars**: Rejected — adds dependency and complexity; fail-fast guards are sufficient for now. Can be added later if variable count grows.
- **Secrets via Docker secrets (swarm)**: Rejected — not needed for single-host Compose; `.env` is the standard for this deployment model.

### Unresolved Objections
- None at this time.

## Applicable Constitution Rules

### Commandments
- Configuration must be explicit, not hidden in defaults. — Source: general best practice

### Negative Constraints
- NEVER commit real secrets to the repository. — Source: `.gitignore` already enforces this.
- NEVER break existing tests without explicit Don approval.

## Acceptance Criteria

1. [ ] `.env.example` exists at repo root with all variables documented.
2. [ ] `backend/db/seed.ts` reads `ADMIN_USERNAME` and `ADMIN_PASSWORD` from env with fallback.
3. [ ] `backend/routes/auth.ts` reads `JWT_SECRET` from env; refuses to boot in production if missing.
4. [ ] `backend/services/ocr.ts` reads `OLLAMA_HOST` and `OLLAMA_MODEL` from env with no hardcoded default.
5. [ ] `backend/db/index.ts` reads `DB_PATH` from env with fallback.
6. [ ] `backend/services/rateFetcher.ts` reads `RATE_API_URL` from env with fallback.
7. [ ] `docker-compose.yml` sources variables via `.env` file and has no inline secrets.
8. [ ] `bun test` in `backend/` passes with zero changes to test files.
9. [ ] App starts successfully in Docker Compose with `.env` copied from `.env.example`.

## Out of Scope

- Frontend env vars (the frontend is a static SPA; any API URL config at build time is unchanged).
- Kubernetes / Helm / Swarm secrets migration.
- Rotation or external secret managers (Vault, AWS Secrets Manager).
- Logging level configuration (can be added in a future Heist).

## Open Risks

- **Risk: Ollama defaults removed break local dev** — Mitigation: `.env.example` contains sensible defaults; devs copy it once.
- **Risk: Docker Compose healthchecks fail if env vars not loaded** — Mitigation: `env_file` is loaded before service start by Docker Compose; `depends_on` healthcheck already ensures Ollama is ready.

## Consigliere Assessment

**Subject:** Contract integrity review for env-migration
**Verdict:** APPROVE WITH CONCERNS

### Findings
1. **HIGH** — FR-002 says "refuse to start" if `JWT_SECRET` missing in production, but the Contract does not specify WHERE this check happens (server.ts boot sequence vs. auth route lazy evaluation). Recommendation: add to boot sequence in `server.ts` immediately after `initDb()`.
2. **MEDIUM** — FR-003 removes all hardcoded defaults for Ollama. If a developer forgets to copy `.env.example`, the service will crash on first OCR call. Recommendation: fail-fast on boot if `OLLAMA_HOST` or `OLLAMA_MODEL` are unset, with a clear message listing the required variables.
3. **LOW** — `.env.example` should explicitly show that `ADMIN_PASSWORD` should be changed in production, with a comment.

### Recommendations
1. Add a startup validation function in `server.ts` that asserts required env vars before `Bun.serve()`.
2. Keep Ollama fail-fast at boot, not at first request.
3. Add `# CHANGE THIS IN PRODUCTION` comments above sensitive defaults in `.env.example`.
