# Contract: Multi-Currency Transaction Tracking

## Objective

Enable the money-tracker app to record transactions in the user's chosen currency while always maintaining and aggregating financial data in the user's default ("home") currency. The system supports both fiat (EUR, USD, GBP, etc.) and crypto (BTC, ETH, SOL, XRP, ADA) currencies. Exchange rates are fetched from free public APIs, cached locally, and stored per-transaction so totals remain historically accurate even if the default currency is changed.

## Architectural Decisions

### AD-001: Integer Storage (Smallest Units)
**Decision:** All monetary values (`amount`, `amount_default`) are stored as INTEGER in the currency's smallest unit (cents for USD, satoshis for BTC, gwei for ETH). A `precision` column on `currencies` determines how many decimals.

**Rationale:** Floating-point arithmetic causes rounding errors that accumulate across thousands of transactions. Integer math is exact. This is a standard accounting practice.

**Rejected:** REAL (float) — rejected in Grilling due to rounding accumulation.

### AD-002: Separate `currencies` Table (Not Hardcoded Enum)
**Decision:** Currencies are rows in a DB table, not a Zod enum. The table is seedable and admin-editable.

**Rationale:** Crypto has hundreds of tickers. A hardcoded enum would require code changes to add currencies. A DB table enables admin management.

**Rejected:** Zod enum + hardcoded list — not extensible enough for crypto.

### AD-003: Dual Rate Sources (frankfurter + CoinGecko)
**Decision:** Fiat rates from frankfurter.app (free, no key, EUR-based). Crypto rates from CoinGecko (free tier, no key for this volume).

**Rationale:** frankfurter is reliable for fiat but doesn't cover crypto. CoinGecko covers both fiat and crypto. Using both: frankfurter for fiat (better reliability), CoinGecko for crypto-only pairs where frankfurter lacks coverage.

**Rejected:** Single CoinGecko for all — less reliable for fiat, different rate structure.

### AD-004: Global Rate Cache (Not Per-User)
**Decision:** One global `exchange_rates` table. All users share the same cache.

**Rationale:** App is single-user for MVP. Per-user caching would multiply API calls by the number of users, hitting rate limits. Global cache means one fetch serves all. When multi-user is added, each user's default currency becomes a base, and cache remains global.

**Rejected:** Per-user rate cache — scales poorly, hits API limits.

### AD-005: Rate Stored Per-Transaction (Not Computed at Query Time)
**Decision:** `exchange_rate` is written at transaction create/edit time and stored in the DB. `amount_default` is computed and stored. Not recalculated on read.

**Rationale:** Exchange rates change over time. The rate at transaction time is the correct one for accounting. Storing it prevents queries from needing to look up historical rates.

**Rejected:** Compute at query time — requires historical rate lookup, complex, inaccurate.

### AD-011: `formatCurrency` Utility
**Decision:** A shared `formatCurrency(amount: number, currencyCode: string)` utility replaces all hardcoded USD formatters. The function reads the currency's precision from a static or reactive currency map and divides the integer amount by `10^precision` before formatting.

**Rationale:** Currently 4+ components call `new Intl.NumberFormat("en-US", { currency: "USD" })` directly. Standardizing via utility ensures all amounts are rendered consistently and respects per-currency precision.

**Rejected:** Per-component individual formatting with hardcoded currency — unmaintainable, error-prone, inconsistent.

### AD-012: Default Currency Seed List
**Decision:** The app seeds the `currencies` table at startup with a curated list of 20 fiat currencies + 5 crypto currencies.

**Rationale:** Provides immediate value without requiring user configuration. Covers 99% of personal finance use cases globally.

**Initial fiat seed:** USD, EUR, GBP, JPY, CHF, CAD, AUD, NZD, SEK, NOK, DKK, PLN, CZK, HUF, RON, BGN, HRK, TRY, MXN, ZAR
**Initial crypto seed:** BTC, ETH, SOL, XRP, ADA

---

### AD-006: SQLite REAL for Rate Column
**Decision:** The `exchange_rate` column on `exchange_rates` and `transactions` is stored as REAL (SQLite float). The conversion formula: `amount_default_smallest = amount_smallest / 10^currency_precision * rate * 10^default_precision`. Rate is stored as decimal (e.g., 1.08345 for EUR/USD).

**Rationale:** DOUBLE precision (15-17 significant digits) is more than sufficient for personal finance rates. 1 EUR = 1.08345 USD fits easily. Even 1 JPY = 0.00000658 BTC has ~11 significant digits — well within DOUBLE limits. BIGINT rates and fixed-point math add complexity without needed precision for this use case.

**Rejected:** 
- INTEGER fixed-point (× 1,000,000): loses precision for very small rates (JPY/BTC). 
- BIGINT with arbitrary precision: over-engineered for this use case. Max realistic transaction in the app is ~$1M (7 digits). Max realistic rate precision needed is ~10 digits. DOUBLE handles 15 digits.

### AD-007: Backend Fetch Only (No Frontend API Calls)
**Decision:** Rate APIs are called only from the backend. The frontend reads from the `/rates` endpoint which serves cached DB data.

**Rationale:** Free APIs like CoinGecko rate-limit by IP. If each user calls from their browser, rate limits are hit faster. Backend caching centralizes this. Also avoids CORS issues and exposes no API keys (even though these APIs don't require keys for free tier).

**Rejected:** Frontend calls API directly — hits rate limits, CORS issues, IP-based throttling.

### AD-008: Default Currency Change Triggers Bulk Recalculation
**Decision:** When the user changes their default currency in Settings, ALL existing transactions' `amount_default` is recalculated using each transaction's stored `exchange_rate`.

**Rationale:** The dashboard and all totals must be consistent. If old transactions keep their old default amounts (e.g., still in USD after switching to EUR), the totals would be a mix of currencies. Recalculation ensures everything is in the same currency.

**Rejected:** Don't recalculate — would produce mixed-currency totals, which is mathematically invalid.

### AD-009: Manual Rate Override Always Available
**Decision:** Even when an auto-suggested rate is available from the cache, the user can manually enter a different rate on the transaction form.

**Rationale:** Public APIs may be stale or unavailable. The user knows the correct rate from their bank statement. Historical accuracy matters more than API convenience.

**Rejected:** API-only rates — would fail when API is down or rate is inaccurate.

### AD-010: Currencies Table Is Global (Shared)
**Decision:** There's one `currencies` table shared by all users. No `user_id` on currencies.

**Rationale:** Adding `user_id` to currencies creates per-user currency lists, which complicates the UI and means two users might create different "BTC" entries with different precision. A global shared table is simpler and correct.

**Rejected:** Per-user currency lists — unnecessary complexity for single-user MVP.

## Grilling Conclusions

### Key Decisions (All Incorporated Above)
- Store amount in original currency + amount_default in home currency
- Integer storage (smallest units) for exact arithmetic
- Currencies database table (seedable, editable)
- Dual APIs: frankfurter (fiat) + CoinGecko (crypto)
- Global rate cache (not per-user) for single-user app
- Recalculate all transactions on default currency change
- Rate stored per-transaction (not computed at read time)
- Manual rate override always available
- Backend-only API fetching
- SQLite REAL for rate column (sufficient precision)

### Rejected Alternatives
- **Manual rate entry only** — Rejected by Don; public API convenience is desired.
- **Fetch from frontend** — Rejected; backend caching is needed for rate limits.
- **Hardcoded currency enum** — Rejected; not extensible for crypto.
- **Per-user currency lists** — Rejected; unnecessary for single-user app.
- **Compute amount_default at query time** — Rejected; breaks historical accuracy.
- **REAL column for amounts** — Rejected; floating-point rounding is unacceptable for money.

### Unresolved Objections (Accepted Risks)
| Objection | Risk | Mitigation |
|-----------|------|------------|
| REAL → INTEGER migration breaks all display math | HIGH | Systematic audit of every `formatCurrency` and `reduce(sum)` call across backend and frontend |
| Two APIs = two failure modes | MEDIUM | Graceful degradation: use cached rate, show warning, user overrides |
| Double precision insufficient for extreme crypto rates | LOW | Edge case (very weak crypto in BTC terms). User can manually override |
| setInterval rate fetch can block event loop | MEDIUM | Use non-blocking `setTimeout` chain; fetch runs in background |
| Scope ~4× original estimate | MEDIUM | Accepted. Architecture is sound; risk is delivery time |
| API downtime makes auto-suggest unavailable | LOW | Falls back to manual entry; user always has override |

## Acceptance Criteria

### Must Pass
1. User can select any currency when creating a transaction.
2. Transaction is saved with `amount` (original + currency), `amount_default`, and `exchange_rate`.
3. If selected currency ≠ default currency, the form auto-suggests a rate from the cache.
4. All dashboard totals show values in the default currency only.
5. Changing default currency in Settings recalculates all existing transactions' `amount_default`.
6. Backend tests pass with new currency fields covered.
7. Frontend displays both original and default amounts on the transaction list.
8. Existing transactions migrate automatically on startup (backfill: currency='USD', amount_default=amount×100, rate=1).
9. Rate cache fetches from frankfurter (fiat) and CoinGecko (crypto) at configured intervals.
10. No paid API keys are used.

### Should Pass
11. Offline mode works with cached rates.
12. Dashboard shows live rates section for used currencies.
13. Admin can add custom currencies.
14. Rate display shows "updated X ago" in the transaction form.
15. Visual warning when cached rate is stale.

### Out of Scope
- Multi-user support (users table exists but transactions aren't user-scoped; deferred)
- Per-currency rate history (only latest cached rate)
- Currency conversion via third-party paid services
- Real-time WebSocket rate updates
- Currency symbol localization (always use stored symbol)
- Tax reporting adjustments for currency fluctuations
- Historical exchange rate graphs
- More than 5 crypto currencies in seed (extensible via admin)

### Open Risks
- **Migration friction:** REAL → INTEGER requires auditing all math across frontend and backend. Mitigation: systematic search/replace with `amount / 100` for display and `amount × 100` for inserts.
- **Rate API changes:** frankfurter.app or CoinGecko could change their API format. Mitigation: well-structured fetch service with validation; graceful degradation to manual override.
- **SQLite WAL timeout on bulk recalculation:** 1000 transactions UPDATE in ~50ms with WAL. Risk is LOW to MEDIUM.
- **Crypto precision edge cases:** Coins with very high precision (e.g., ETH at 18 decimals) may not fit comfortably in SQLite INTEGER max. Mitigation: cap precision at 9 (gwei-level) for ETH; sufficient for personal finance.
