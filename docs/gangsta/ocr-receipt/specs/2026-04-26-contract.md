# Contract: OCR Receipt-to-Transaction Feature

## Objective
Add the ability to create a transaction by uploading an image, taking a camera photo, or submitting a physical receipt photograph. Use Ollama with the qwen3-vl:235b-cloud vision model to extract transaction fields (amount, currency, date, description, type, category) from the image. The extracted data is presented to the user as a suggestion for review and confirmation before creating the transaction.

## Requirements

### Functional Requirements

#### FR-001: Image Upload Support
The frontend shall support receipt image upload via: drag-and-drop onto a designated area, standard file picker (accepting JPEG, PNG, WEBP), and direct camera capture using the device getUserMedia API.

#### FR-002: OCR Extraction Backend
A new backend endpoint shall accept multipart image uploads, validate the file type, forward the image to a local Ollama instance running the qwen3-vl:235b-cloud model, and return a structured JSON suggestion containing extracted transaction fields.

#### FR-003: Structured Prompt Engineering
The extraction prompt sent to the vision model shall: instruct the model to return only valid JSON, include the list of known transaction categories and active currencies as context, require amount as a plain numeric string (no currency symbols, no comma separators), require currency as a 3-letter ISO 4217 code, require date as YYYY-MM-DD, and require category as one of the known categories or null.

#### FR-004: Post-OCR Sanity Validation
After receiving the model's JSON response, the backend shall run business-logic sanity checks: amount must parse to a number greater than 0 and less than 1,000,000; date must be within the last 5 years; currency must exist in the app's supported-currency set. The endpoint shall return a confidence score (high, medium, low) based on how many checks pass cleanly.

#### FR-005: Explicit User Confirmation
Extracted values shall be displayed in a read-only preview card in the transaction form. The user must click an explicit "Apply Scan" button before values are copied into the editable form. This prevents accidental submission of model hallucinations.

#### FR-006: Form State Preservation
When the user enters OCR mode, the current manual form values shall be snapshotted. If the user cancels OCR without applying, the snapshot shall be restored. If the user applies the scan, the snapshot is discarded and replaced with OCR values.

#### FR-007: Receipt Image Persistence
On successful transaction creation, the receipt image shall be moved from a temporary location to a permanent location keyed by transaction ID. A new endpoint shall serve the receipt image by transaction ID with safe Content-Type headers and nosniff protection.

#### FR-008: Testable LLM Boundary
The Ollama client shall be wrapped behind an injectable service interface so the backend tests can mock the LLM call without requiring a running Ollama instance.

#### FR-009: Scoped MVP
Email receipts, HTML e-receipts, and PDF uploads are explicitly out of scope for this Heist. Only camera/file uploads of physical receipt images (JPG, PNG, WEBP) are supported.

### Non-Functional Requirements

#### NFR-001: Local-First Deployment
The feature assumes a single-user or small-team local deployment with a local Ollama instance. No background job queue, no rate limiting, and no distributed file storage are required for the MVP.

#### NFR-002: filesystem-based Receipt Storage
Receipt images shall be stored on the local filesystem only, with zero new database columns or schema migrations. The storage path shall be deterministic (based on transaction ID) and shall not rely on database rows for lookup.

#### NFR-003: Hono Route Ordering Safety
The receipt image route GET /transactions/:id/receipt shall be registered explicitly before the parameterized GET /:id route in the Hono router to avoid silent shadowing and 404 failures.

#### NFR-004: Safe File Handling
All user-provided filenames shall be sanitized before any filesystem interaction. The extension shall be extracted and whitelisted (jpg, jpeg, png, webp). No user-provided filename shall ever become a path component.

#### NFR-005: MIME Validation Before Disk Write
The file type shall be validated against an allowlist (image/jpeg, image/png, image/webp) before any data is written to disk or forwarded to the model.

#### NFR-006: API Client Isolation
The existing JSON-only API client shall not be modified to support multipart. A dedicated uploadReceipt method shall be added alongside the existing JSON methods, avoiding header pollution or content-type conflicts.

#### NFR-007: Zero Database Migration
No ALTER TABLE operations shall be introduced. Receipt images are stored and served purely via filesystem paths derived from the transaction ID.

## Architectural Decisions

### AD-001: Backend-Only OCR Proxy
The frontend never talks directly to Ollama. The backend acts as a proxy. Rationale: avoids CORS issues, hides model configuration and URL from the client, and centralizes prompt engineering.

### AD-002: Zero-Migration Filesystem Persistence
Receipt images are stored on disk with no database schema changes. Rationale: Keeps the scope minimal and avoids migration risk in a raw-SQL SQLite codebase.

### AD-003: Strict Image Validation
MIME type and extension whitelisting enforced before any disk write or model call. Rationale: Prevents malicious uploads without adding heavy parsing libraries.

### AD-004: Injectable LLM Service Interface
The Ollama client is wrapped behind an OcrService class with extractReceipt(). Rationale: Makes the LLM boundary fully mockable in CI without running Ollama.

### AD-005: Dedicated Multipart Upload Method
A new uploadReceipt() API method handles FormData and omits the JSON content-type header. Rationale: Isolates multipart logic from the existing JSON-focused API client, preventing accidental content-type conflicts.

### AD-006: Explicit Confirmation Barrier
OCR results populate a read-only preview card; an Apply Scan button is required to copy into the form. Rationale: Prevents accidental submission of model hallucinations. Selected by unanimous consensus after Grilling debate.

### AD-007: Snapshot/Restore Form State
Manual form values are snapshotted when entering OCR mode and restored on cancel. Rationale: Guarantees no data loss when switching between manual entry and receipt scanning.

## Grilling Conclusions

### Key Decisions
- **OCR proxy remains synchronous** (Don overruled async/queue concerns): Single-user local deployment assumed. Accepted risk documented.
- **No rate limiting or upload size constraints for MVP** (Don overruled): Operational deployment handles enforcement via reverse proxy. Accepted risk documented.
- **JSON fragility mitigated by Zod + clean prompt engineering** (Don overruled): Model instructed to return clean JSON. Zod validation catches malformed output. Accepted risk documented.
- **Category suggestions included in prompt, not auto-selected**: OCR prompt lists available categories and currencies. Frontend shows suggestion as placeholder but never pre-selects the category field.
- **Filesystem-only persistence confirmed**: Zero DB migration. Images stored at data/receipts/{transaction_id}.{ext}.
- **Apply Scan confirmation barrier**: OCR values shown in read-only preview; explicit button required to populate form (selected by Don).
- **State snapshot/restore on cancel**: Manual values saved before entering OCR mode, restored on cancel (selected by Don).

### Rejected Alternatives
- **Direct Ollama call from frontend**: Rejected — exposes model URL and config; CORS complications.
- **Persistent DB column for receipt path**: Rejected by Don — insists on zero migration.
- **Auto-populate form fields without confirmation**: Rejected by Don after Grilling — confirmation barrier required.
- **E-receipt support (email/HTML/PDF)**: Out of scope for this MVP.
- **Async background job / queue for OCR**: Rejected by Don as over-engineered for local use.

### Unresolved Objections
- **Synchronous 235B model call blocks Bun event loop** — Risk: MEDIUM — Mitigation: Don accepted as local deployment risk. Documented as future improvement if concurrent usage arises.
- **No file size limits or rate limiting** — Risk: MEDIUM — Mitigation: Trusted local-network usage. Reverse proxy or nginx recommended for production deployment.

## Applicable Constitution Rules

### Commandments
- Reuse existing patterns (Hono routes, Zod validation, raw SQL, Svelte runes state) — Source: existing codebase and previous money-tracker Heist.
- No Drizzle ORM insertions for new features — Source: existing backend uses raw SQL.
- Shared schemas in shared/ package consumed by both frontend and backend — Source: existing monorepo pattern.

### Negative Constraints
- NEVER introduce database schema migrations for this feature — Don explicitly mandated filesystem-only persistence.
- NEVER auto-populate the transaction form with OCR values without explicit user action (Apply Scan button) — Don explicitly mandated confirmation barrier.
- NEVER expose Ollama URL or model configuration to the frontend — Source: Grilling consensus.

## Acceptance Criteria

1. User can upload a receipt image (drag-and-drop, file picker, or camera capture) from the transaction form.
2. Backend accepts the image, validates MIME type and extension, and forwards to local Ollama with a structured prompt.
3. Backend returns a JSON suggestion with amount, currency, date, description, and category fields plus a confidence score.
4. Frontend displays the suggestion in a read-only preview card with Apply Scan and Discard actions.
5. Clicking Apply Scan copies values into the transaction form; user can edit before saving.
6. Clicking Discard restores the previous manual form values.
7. On successful transaction save, the receipt image is persisted and served via GET /transactions/:id/receipt.
8. Backend tests mock the Ollama boundary and do not require a running Ollama instance.
9. All existing backend tests continue to pass (no regressions).
10. Frontend build completes without errors.

## Out of Scope
- Email receipts, HTML e-receipts, PDF uploads
- Rate limiting and file size constraints
- Background async job queue for OCR processing
- Cloud blob storage (S3, etc.)
- OCR confidence-based auto-categorization or auto-approval
- Image preprocessing (de-skew, rotate, enhance)
- Multi-currency conversion during OCR extraction (amount and currency extracted as-is; conversion handled by existing transaction logic)

## Open Risks
- Ollama qwen3-vl:235b-cloud must be pulled and running locally for the feature to work in production.
- Receipt images stored on node-local filesystem will be lost if the backend is containerized with an ephemeral filesystem or load-balanced across multiple nodes.
- Prompt injection via adversarial images can produce structurally valid but factually wrong suggestions. Mitigated by sanity-check layer + explicit user confirmation.
