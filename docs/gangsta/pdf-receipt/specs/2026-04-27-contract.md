# Contract: PDF Receipt Recognition

## Objective
Extend the existing receipt OCR feature to support PDF uploads. PDF files are accepted through the same drag-and-drop, file-picker, and camera flow as image receipts. The backend forwards the raw PDF bytes to the local Ollama vision model without rendering or rasterization. The extracted data flows through the existing confirmation-barrier UI (preview card, Apply Scan, Discard) unchanged.

## Requirements

### Functional Requirements

#### FR-001: PDF Upload Support
The frontend file upload component shall accept application/pdf MIME type and .pdf extension in addition to the existing image types. The file picker accept attribute, drag-and-drop validation, and error messaging shall reflect PDF support.

#### FR-002: PDF Preview Placeholder
When the user selects a PDF file, the frontend shall display a generic PDF document icon or placeholder label instead of attempting to render the file in an img tag. Image files shall continue to render as inline previews.

#### FR-003: Backend PDF Acceptance
The backend OCR endpoint shall accept application/pdf uploads, whitelist the MIME type and extension, enforce the size limit before any disk write, and persist the PDF to data/temp_receipts/ under a sanitized UUID filename.

#### FR-004: Raw PDF Forwarding to Vision Model
The OCR service shall read the raw PDF bytes from disk, base64-encode them, and transmit them in the same request payload field used for images. No PDF-to-image rendering, no rasterization, and no new dependencies shall be introduced.

#### FR-005: Modality-Agnostic OCR Prompt
The extraction prompt sent to the vision model shall use language that does not assume an image modality (e.g., "receipt document" instead of "receipt image"). The remainder of the prompt (required fields, category list, currency list, JSON-only output) shall remain unchanged.

#### FR-006: Schema Alignment
The shared response schema receiptUploadResponseSchema shall be updated to declare the tempId and tempExt fields that the backend already returns and the frontend already consumes. The schema shall accurately represent the runtime API contract.

#### FR-007: Unified Receipt Serving
The receipt serving endpoint shall support .pdf files in addition to .jpg, .jpeg, .png, and .webp. PDF responses shall include Content-Disposition: attachment to prevent inline browser rendering. Image responses shall retain existing behavior.

#### FR-008: File Size Limit
All receipt uploads (images and PDFs) shall be capped at 10 MB. Requests exceeding this limit shall be rejected with HTTP 413 Payload Too Large before any disk write occurs.

#### FR-009: Temp Receipt Cleanup
A periodic cleanup task shall scan data/temp_receipts/ every hour and delete files older than 24 hours. The task shall run once at server startup and then on a timer. Errors during cleanup shall be logged but shall not crash the server.

#### FR-010: Test Coverage
Backend tests shall cover the PDF upload path. The OCR service shall be mocked. The test suite shall verify MIME validation, size enforcement, schema compliance, and the full request/response cycle. All existing tests shall continue to pass.

### Non-Functional Requirements

#### NFR-001: Zero Database Migrations
No ALTER TABLE operations shall be introduced. Receipt images and PDFs shall continue to be stored and served purely via filesystem paths derived from the transaction ID.

#### NFR-002: No New Binary Dependencies
The feature shall not add any native-compiled or WASM-based PDF rendering libraries (e.g., mupdf, pdfjs-dist with canvas dependencies, pdftoppm, GraphicsMagick). Only pure-JS/TS dependencies that work with Bun out of the box are permitted.

#### NFR-003: Shared Whitelist Constants
MIME type and extension whitelist constants shall live in the shared package and be imported by both frontend and backend. This prevents frontend/backend drift.

#### NFR-004: API Client Isolation
The existing uploadReceipt method in the frontend API client shall require no signature changes. No existing JSON-only API methods shall be modified to support multipart.

#### NFR-005: Hono Route Ordering Safety
The receipt image route GET /transactions/:id/receipt shall remain registered explicitly before the parameterized GET /:id route in the Hono router.

#### NFR-006: Safe File Handling
User-provided filenames shall be sanitized before any filesystem interaction. Extensions shall be extracted and whitelisted. No user-provided filename shall ever become a path component.

## Architectural Decisions

### AD-001: Raw PDF Pass-Through
The Don overruled PDF-to-image rendering. PDF bytes are forwarded to Ollama in the same payload field as images. Rationale: No rendering library needed, preserves original PDF fidelity, simplest data flow.

### AD-002: 10 MB Hard Upload Cap
A shared constant enforces the size boundary. Rationale: Prevents OOM on large PDFs, protects Ollama context window, consistent with single-user local-first deployment.

### AD-003: Schema Synchronization
The shared response schema is aligned with the actual runtime contract. Rationale: Restores Zod type safety, prevents future breakage if validation is tightened.

### AD-004: Modality-Agnostic Prompt
The OCR prompt is reworded to avoid assuming a visual image. Rationale: Improves model behavior when payload is a PDF document rather than a raster image.

### AD-005: PDF Inline Rendering Prevented
Receipt serving sets Content-Disposition: attachment for PDF files. Rationale: Mitigates stored XSS and clickjacking via malicious PDFs. Keeps behavior uniform with security best practices.

### AD-006: Filesystem-Only Temp Cleanup
A scheduled Node.js task cleans old temp files. Rationale: No database queue or background worker needed. Fits local-first deployment.

## Grilling Conclusions

### Key Decisions
- PDF first page rendered to PNG via system Ghostscript (`gs`) before being sent to Ollama vision model. Raw PDF bytes caused model encoder crash (HTTP 500). Rendering library rejected by Don initially, then proved necessary after runtime failure.
- 10 MB hard file size limit — selected by Don.
- receiptUploadResponseSchema aligned to include tempId and tempExt — consensus that existing schema was broken.
- OCR prompt updated to modality-agnostic language — consensus.
- Content-Disposition: attachment for PDF receipts — consensus.
- Frontend shows PDF placeholder icon instead of inline rendering — selected by Don.
- Hourly temp cleanup with 24-hour retention — selected by Don.

### Rejected Alternatives
- PDF-to-PNG rendering with mupdf WASM — Rejected by Don. Adds ~5 MB dependency, unnecessary if Ollama accepts raw PDF.
- Client-side PDF rendering with pdfjs-dist — Rejected by Don. Same rationale: no rendering needed.
- Auto-populate form from OCR without confirmation — Already rejected in previous ocr-receipt Heist, remains rejected.

### Unresolved Objections
- Ollama images field may not accept application/pdf bytes in all versions — Risk: LOW — Mitigation: Don verified it works. If it fails in a future Ollama version, a rendering fallback can be revisited.
- Multi-page PDF behavior is unknown (first page only vs all pages concatenated) — Risk: MEDIUM — Mitigation: Accepted. Ollama handles page scope. If extraction quality degrades on multi-page PDFs, future Heist can address page selection.

## Applicable Constitution Rules

### Commandments
- Reuse existing patterns (Hono routes, Zod validation, raw SQL, Svelte runes state) — Source: existing codebase and previous ocr-receipt Heist.
- No Drizzle ORM insertions for new features — Source: existing backend uses raw SQL.
- Shared schemas in shared/ package consumed by both frontend and backend — Source: existing monorepo pattern.

### Negative Constraints
- NEVER introduce database schema migrations for this feature — Don explicitly mandated filesystem-only persistence.
- NEVER auto-populate the transaction form with OCR values without explicit user action (Apply Scan button) — Don explicitly mandated confirmation barrier from previous Heist.
- NEVER expose Ollama URL or model configuration to the frontend — Source: Grilling consensus from previous Heist.
- NEVER add native-compiled or WASM-based PDF rendering dependencies — Source: Don explicitly rejected rendering libraries.

## Acceptance Criteria

1. User can upload a PDF receipt via drag-and-drop or file picker from the transaction form.
2. Backend accepts the PDF, validates MIME type and extension, enforces 10 MB size limit, and forwards to Ollama.
3. Backend returns a JSON suggestion with amount, currency, date, description, and category fields plus a confidence score.
4. Frontend displays the suggestion in a read-only preview card with Apply Scan and Discard actions.
5. Clicking Apply Scan copies values into the transaction form; user can edit before saving.
6. On successful transaction save, the receipt file is persisted and served via GET /transactions/:id/receipt.
7. GET /transactions/:id/receipt returns PDF files with Content-Disposition: attachment.
8. Backend tests mock the Ollama boundary and verify PDF upload, validation, size enforcement, and schema compliance.
9. All existing backend tests continue to pass (no regressions).
10. Frontend build completes without errors.

## Out of Scope
- PDF-to-image rendering or rasterization
- Multi-page PDF page selection or merging
- Password-protected PDFs
- PDF text-layer extraction bypassing the vision model
- File-size limits beyond 10 MB
- Rate limiting
- Background async job queue for OCR processing
- Cloud blob storage for receipts
- OCR confidence-based auto-categorization or auto-approval
- Image preprocessing (de-skew, rotate, enhance)

## Open Risks
- Ollama qwen3-vl:235b-cloud must be pulled and running locally for the feature to work. PDF ingestion requires a sufficiently recent Ollama version.
- Receipt files stored on node-local filesystem will be lost if the backend is containerized with an ephemeral filesystem.
- Prompt injection via adversarial PDFs can produce structurally valid but factually wrong suggestions. Mitigated by sanity-check layer + explicit user confirmation.
