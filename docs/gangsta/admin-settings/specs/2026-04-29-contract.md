# Contract: Admin Settings

## Objective

Create a dedicated Admin Settings page (`#/admin`) for the Money Tracker application, extracting admin functionality from the existing `Settings.svelte` kitchen-sink component into its own route. The admin page provides: (1) a paginated list of registered users with CRUD operations, (2) a registration toggle controlling `system_config.allow_registration`, (3) a database cleanup system with two-step confirmation tokens for safe destructive operations, and (4) an audit log recording all destructive admin actions.

## Requirements

### Functional Requirements

**FR-001** — Dedicated Admin Route: A new `#/admin` hash route in `App.svelte`, accessible only to users with `role === "admin"`. Non-admins are redirected to `#/dashboard`. An "Admin" nav link appears in the navbar for admin users only.

**FR-002** — Stats Dashboard: The admin page displays aggregate system metrics (total users, total transactions, total categories, total exchange rates) sourced from `GET /admin/stats`. Read-only display, no interaction.

**FR-003** — Registration Toggle: A toggle switch controlling `system_config.allow_registration`. Uses the shared `settings.svelte.ts` store for state — no duplication with `Settings.svelte`. Changing the toggle calls `PUT /admin/config/:key` and updates the shared store.

**FR-004** — Paginated User List: A table showing user ID, username, email, role, and creation date. Supports pagination via `GET /admin/users` with optional `?page=&limit=` query parameters. Default response (no params) returns full array for backward compatibility. Create and delete user operations use existing endpoints.

**FR-005** — Two-Step Cleanup Confirmation: Destructive database operations require a two-step flow: (1) frontend requests a single-use confirmation token via `POST /admin/cleanup/token` specifying the scope, (2) frontend shows a confirmation modal, (3) frontend submits `POST /admin/cleanup` with the token and scope. Tokens are stored in a dedicated `cleanup_tokens` table with per-user scoping, expiry, and consumed tracking.

**FR-006** — Cleanup Operations: Two cleanup scopes are supported:
- `transactions`: Deletes all rows from the `transactions` table. Wrapped in a `transaction()` block.
- `orphaned`: Deletes stale consumed refresh tokens (`consumed = 1 AND expires_at < now()`) and orphaned non-predefined categories (`user_id IS NULL AND is_predefined = 0`). Wrapped in a `transaction()` block.

**FR-007** — Cleanup Token Security: Tokens are single-use, expire after 5 minutes, are scoped to both the requesting user and the specific cleanup scope (e.g., a token requested for scope `transactions` cannot be used for scope `orphaned`), and are invalidated upon consumption. Rate limit: 1 token request per user per 60 seconds. Expired tokens are cleaned up opportunistically. Rate limit violations return HTTP 429 with a descriptive message.

**FR-008** — Audit Logging: All destructive admin operations (user deletion, config changes to `allow_registration`, cleanup operations) write an entry to the `audit_log` table recording: action, performed_by (user ID), scope, details (JSON string with context: e.g., `{"deleted_user_id": 5, "deleted_count": 42}` for user deletion, `{"scope": "transactions", "rows_affected": 150}` for cleanup), and timestamp. Audit log entries are written AFTER the transaction commits (not inside it) to ensure they persist even if the transaction rolls back (per C-3). The `performed_by` column uses `ON DELETE SET NULL` so audit records survive admin user deletion. A `GET /admin/audit` endpoint returns the last 50 audit entries for display in the admin UI.

**FR-009** — Admin Tab Extraction: The admin tab in `Settings.svelte` (approximately 150 lines of state, handlers, and template) is removed. `Settings.svelte` retains only user-facing settings (general, currencies, categories). The `errors` object is preserved with its other keys.

**FR-010** — Admin State Management: A new `state/admin.svelte.ts` manages admin-specific state (users list, stats, cleanup operations, audit log). The existing `settings.svelte.ts` is extended to include `allow_registration` and `system_config` state — this is new functionality added to the store, not pre-existing. The Admin page imports the extended `settings.svelte.ts` for the registration toggle.

**FR-011** — Config Key Centralization: The `"allow_registration"` config key string is extracted to `backend/lib/config-constants.ts` as `CONFIG_KEYS.ALLOW_REGISTRATION`. All references in `admin.ts` and `auth.ts` use this constant (NC-2 compliance).

### Non-Functional Requirements

**NFR-001** — Transaction Safety: All multi-table cleanup operations are wrapped in `transaction()` blocks. If any operation fails, all changes roll back. No partial data destruction is permitted. Audit log entries are written AFTER the transaction commits, not inside it, to ensure they persist even on rollback (per C-3). The existing `DELETE /admin/users/:id` endpoint is updated to wrap its cascade deletes in a `transaction()` block as well.

**NFR-002** — Confirmation Token Integrity: Tokens are generated using `crypto.randomUUID()`. The raw token is returned to the requester in the `POST /admin/cleanup/token` response. The token is immediately hashed with `Bun.CryptoHasher("sha256")` before storage in the `cleanup_tokens` table — only the hash is stored (per C-1). Token validation hashes the submitted token and compares with the stored hash. Validation checks: hash exists in DB, not consumed, not expired, belongs to requesting user, scope matches.

**NFR-003** — Per-User Rate Limiting: Cleanup token requests are rate-limited per `userId` (not per IP). Maximum 1 token request per user per 60 seconds. This is enforced at the handler level, not via the existing IP-based rate limiter.

**NFR-004** — Backward Compatibility: `GET /admin/users` without pagination params returns the full user array (current behavior). Pagination is opt-in via query parameters.

**NFR-005** — Frontend Auth Guard: The `#/admin` route renders nothing until `auth.user?.role === "admin"` is confirmed. Non-admins are immediately redirected to `#/dashboard`. The backend `adminMiddleware` remains the authoritative access control.

**NFR-006** — SQLite Compatibility: New tables (`audit_log`, `cleanup_tokens`) use SQLite-compatible column types and constraints. `PRAGMA foreign_keys = ON` is already enabled in the application.

**NFR-007** — No Frontend Tests This Heist: Frontend tests remain at zero. This heist adds backend tests only.

**NFR-008** — Constitution Compliance: All implementation respects the 6 Commandments and 4 Negative Constraints from the Project Constitution.

## Architectural Decisions

**AD-001** — Separate `/admin` route over admin tab in Settings: Admin functionality has grown beyond what fits in a tab. A dedicated page provides separation of concerns, room for future admin features, and cleaner state management. Don approved this over the DA's counter of extracting into a component within Settings.

**AD-002** — Dedicated `cleanup_tokens` table over `system_config` row: Confirmation tokens need TTL, user scoping, and consumption tracking — none of which `system_config` supports. A dedicated table provides proper semantics and avoids conflating configuration with operational state.

**AD-003** — `purge_transactions` and `purge_orphaned` scope only, no `purge_user_data`: The existing `DELETE /admin/users/:id` with cascade already handles per-user data deletion. Adding a separate `purge_user_data` would create overlapping semantics. The two chosen scopes (all transactions, orphaned data) address distinct operational needs without duplication.

**AD-004** — `POST /admin/cleanup/token` not GET: Token creation is a state mutation. HTTP semantics require POST for side effects. GET pre-fetches or proxy caches could silently invalidate tokens.

**AD-005** — Shared `settings.svelte.ts` for registration toggle: The `allow_registration` config is already managed by the settings store. Duplicating this state in `admin.svelte.ts` would create stale data bugs. The Admin page imports the existing store.

**AD-006** — Backend-only config constants module: The `"allow_registration"` key string appears in backend files only (`admin.ts`, `auth.ts`). Creating `backend/lib/config-constants.ts` satisfies NC-2. A cross-package `shared` module for a single key would be premature abstraction (DA's point, accepted).

## Grilling Conclusions

### Key Decisions
- Separate `/admin` route (not a tab in Settings): Cleaner architecture, room to grow (Don approved)
- Web UI for cleanup with strong safeguards (not CLI-only): Convenient admin UX with confirmation tokens, rate limiting, and audit logging (Don approved)
- Audit log required: New `audit_log` table recording all destructive admin operations
- Shared state store: Admin page uses `settings.svelte.ts` for registration toggle, new `admin.svelte.ts` for admin-only state
- Backend tests required, frontend tests deferred
- Two cleanup scopes: `transactions` and `orphaned` — no `purge_user_data` (overlaps existing DELETE endpoint)

### Rejected Alternatives
- Extract admin into component within Settings: Don rejected — separate route provides better separation and maintainability
- CLI-only cleanup operation: DA's alternative — Don rejected; web UI with safeguards provides better admin UX
- `system_config` row for tokens: DA identified as infeasible — no TTL/expiry columns; dedicated table required
- `purge_user_data` cleanup scope: Overlaps existing `DELETE /admin/users/:id` with cascade; removed from scope
- Cross-package shared constants for one key: Premature abstraction; backend-only module sufficient

### Unresolved Objections
- None — DA CONCEDEd in Round 2 with specifiable conditions, all addressed in the final synthesis

### Database Schema Definitions

**`cleanup_tokens` table:**
```
cleanup_tokens
  id            INTEGER PRIMARY KEY AUTOINCREMENT
  token_hash    TEXT NOT NULL UNIQUE
  user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE
  scope         TEXT NOT NULL CHECK(scope IN ('transactions', 'orphaned'))
  consumed      INTEGER NOT NULL DEFAULT 0
  expires_at    INTEGER NOT NULL  (unix timestamp, now + 300 seconds)
  created_at    INTEGER NOT NULL DEFAULT (unixepoch())
```
Index: `idx_cleanup_tokens_user_id ON cleanup_tokens(user_id)`

**`audit_log` table:**
```
audit_log
  id            INTEGER PRIMARY KEY AUTOINCREMENT
  performed_by INTEGER REFERENCES users(id) ON DELETE SET NULL
  action       TEXT NOT NULL
  scope         TEXT
  details       TEXT
  ip_address   TEXT
  created_at    INTEGER NOT NULL DEFAULT (unixepoch())
```
Index: `idx_audit_log_performed_by ON audit_log(performed_by)`
Index: `idx_audit_log_created_at ON audit_log(created_at)`

### Response Shape Definitions

**`GET /admin/stats` response:**
```json
{ "users": number, "transactions": number, "categories": number, "exchange_rates": number }
```

**`GET /admin/users` (without params) response:**
```json
[ { "id": number, "username": string, "email": string | null, "role": string, "created_at": number } ]
```

**`GET /admin/users?page=1&limit=10` response:**
```json
{ "items": [...], "total": number, "page": number, "limit": number }
```

**`POST /admin/cleanup/token` response:**
```json
{ "token": string }
```
(Note: the raw token is returned to the requester once. Only the hash is stored.)

**`POST /admin/cleanup` response:**
```json
{ "affected_rows": number, "scope": string }
```

## Out of Scope

- Frontend tests (no test infrastructure exists in frontend)
- E2E tests
- Per-userId rate limiting for non-cleanup endpoints (only cleanup token requests are rate-limited per-userId)
- Admin dashboard analytics or charts (stats cards with counts only)
- CSRF protection (existing Bearer token auth model)
- Audit log UI pagination beyond last 50 entries
- Role change endpoint (`PUT /admin/users/:id/role`) — not in Don's request

- Database nuke/reset operation (too dangerous, no legitimate use case)

## Open Risks

**Risk-001** — Settings.svelte extraction complexity: The admin tab removal touches approximately 150 lines including some shared reactive state. While the extraction is mechanical, the shared `errors` object requires careful handling. **Mitigation:** Test existing Settings tabs (general, currencies, categories) thoroughly after extraction. **Severity:** LOW

**Risk-002** — SQLite busy contention during large cleanup: `DELETE FROM transactions` on a large dataset could lock the database. **Mitigation:** `PRAGMA busy_timeout = 5000` is already set (`db/index.ts`). Document that cleanup should be performed during low-traffic periods. Future enhancement: batch deletes. **Severity:** MEDIUM

**Risk-003** — `SELECT COUNT(*)` performance on large tables: Full table scan for stats. **Mitigation:** Stats are admin-only and infrequently accessed. Future enhancement: `sqlite_stat1` approximate counts. **Severity:** LOW
