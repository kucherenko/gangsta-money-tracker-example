# Contract: Auth & Multi-User

## Objective

Transform the Money Tracker from a single-admin-user application into a multi-user system with proper JWT authentication (access + refresh tokens with rotation), user registration, per-user data isolation, and admin-controlled user management — while preserving all existing functionality and migrating existing data to the admin user.

## Requirements

### Functional Requirements

**Authentication**
1. FR-001: Users can log in with username and password, receiving a JWT access token (15-minute expiry) and an opaque refresh token (7-day expiry)
2. FR-002: Auth middleware verifies JWT access tokens via hono/jwt signature verification — no database lookup per request
3. FR-003: Users can refresh their access token by presenting a valid refresh token; the old refresh token is invalidated and a new one is issued (rotation)
4. FR-003a: If a previously-rotated (invalidated) refresh token is resubmitted, all refresh tokens for that user are revoked, forcing re-authentication — this detects token theft
4. FR-004: Users can log out, which revokes their refresh token server-side
6. FR-005: Users can change their password, which invalidates all their refresh tokens; the current 15-minute access token remains valid until expiry (stateless JWT cannot be retroactively invalidated)
6. FR-006: Rate limiting on auth endpoints: login (10/15min), register (5/hour), refresh (30/15min)

**Registration & User Management**
7. FR-007: New users can self-register when `allow_registration` is enabled in system config
8. FR-008: Registration is closed by default; admin must explicitly enable it via settings
9. FR-009: Admin can create users directly via admin-only endpoint regardless of registration toggle
10. FR-010: Admin can delete users with cascade deletion of all user data (transactions, custom categories, settings, refresh_tokens, receipt files); admin cannot delete themselves
11. FR-011: Admin can list all users via admin-only endpoint
12. FR-012: Admin can toggle `allow_registration` via admin-only system config endpoint
13. FR-013: Usernames must be 3-30 characters, alphanumeric plus underscore, unique
14. FR-014: Passwords must be 8-128 characters (max prevents hashing DoS via oversized passwords)
15. FR-015: Email field is optional on users for future password reset use; when provided, email must be unique across all users

**Data Isolation**
16. FR-016: Every data query (transactions, categories, dashboard, settings) is scoped by the authenticated user's ID
17. FR-017: A user cannot access another user's data — including admin users (private data model)
18. FR-018: Predefined categories are global (user_id IS NULL) and read-only; users can create custom categories with their own user_id
19. FR-019: Custom categories cannot duplicate the name+type of predefined categories
20. FR-020: Each user has their own settings row (per-user default currency, fetch intervals, etc.)
21. FR-021: Currency recalculation (on default currency change) only affects the requesting user's transactions
22. FR-022: Receipt files are stored in user-scoped directories

**Frontend**
23. FR-023: Login page provides username/password entry with link to registration (when enabled)
24. FR-024: Registration page with username, email (optional), password, confirm password
25. FR-025: Frontend stores access token and refresh token in localStorage
26. FR-026: Frontend implements mutex-locked automatic token refresh on 401 responses with concurrent request deduplication; failed refresh (expired/invalid refresh token) redirects user to login page
27. FR-027: Settings page shows Admin tab (visible only to admin role) with user management and registration toggle
28. FR-028: Navigation shows current user identity and logout button

**Database & Migration**
29. FR-029: Existing `users.token` column is removed (table recreation migration); `role` and `email` columns are included in the new table definition
30. FR-030: Users table recreated with `role` column (TEXT, default 'user') and `email` column (TEXT, nullable, unique)
31. FR-031: `user_id` column added to `transactions` and `categories` tables
32. FR-032: `refresh_tokens` table created for storing hashed refresh tokens with expiry and user association
33. FR-033: `system_config` table created for global configuration (allow_registration, etc.)
34. FR-034: All existing transactions and categories are assigned to the admin user (user_id = 1)
35. FR-035: Existing receipt files are migrated from flat directory to user-scoped subdirectories
36. FR-036: Existing sessions are invalidated (acceptable breaking change)
37. FR-037: Admin user is seeded on startup with username from `ADMIN_USERNAME` env var and password from `ADMIN_PASSWORD` env var; admin user always has role 'admin'
38. FR-038: Rate limiting returns HTTP 429 with JSON body `{ error: "Too many requests" }` and `Retry-After` header
39. FR-039: New users receive default settings (default_currency: USD, fiat_fetch_interval: 24h, crypto_fetch_interval: 1h, auto_fetch_rates: true, show_crypto_on_dashboard: true) created automatically via ensureSettingsRow

### Non-Functional Requirements

1. NFR-001: JWT verification is stateless — no database query required for normal authenticated requests
2. NFR-002: Refresh token rotation uses `BEGIN IMMEDIATE` transactions to prevent race conditions under concurrent refresh attempts
3. NFR-003: SQLite pragmas: `journal_mode = WAL`, `busy_timeout = 5000`, `foreign_keys = ON` (enabled after orphan data cleanup)
4. NFR-004: Foreign key constraints are enforced; orphaned data is cleaned before enabling FK pragmas
5. NFR-005: Composite indexes on (user_id, date) for transactions and (user_id) for categories ensure query performance doesn't degrade with per-user filtering
6. NFR-006: Refresh tokens are stored as hashes — database compromise does not leak working tokens
7. NFR-007: Rate limiting uses in-memory store (suitable for single-server SQLite app)
8. NFR-008: Migration order guarantees admin user exists before user_id backfill runs
9. NFR-009: JWT signing secret is sourced from `JWT_SECRET` environment variable (minimum 32 characters); validated at startup; rotation requires server restart
10. NFR-010: Password hashing uses bcrypt with cost factor 12 (already in use via bcryptjs dependency)

## Architectural Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Auth model | JWT access + opaque refresh tokens with rotation | Don's decision. Stateless verification for performance; refresh tokens enable logout and revocation |
| Token storage (frontend) | localStorage for both tokens | PWA compatibility; service workers cannot access httpOnly cookies. XSS risk accepted with 15min access token TTL mitigation |
| Category ownership | Hybrid: single table with user_id NULL for predefined, user_id set for custom | Don's decision. No duplication; simpler FKs; predefined stay globally readable |
| Data access model | Private — admin cannot see other users' data | Don's decision. Financial data is private |
| Registration default | Closed by default | Don's decision. Personal finance app should be restrictive by default |
| User deletion | Hard delete with cascade | Don's decision. All user data removed on deletion |
| Global config | Separate `system_config` table, not in per-user `settings` | Clean separation of system-wide vs. user-specific configuration |
| Admin middleware | Role-based check on `users.role` column | Extensible to more roles later; simple boolean check for now |
| Migration approach | Table recreation for users (token column removal); ALTER TABLE ADD COLUMN for user_id additions | Required due to SQLite DROP COLUMN limitations |

## Grilling Conclusions

### Key Decisions
- JWT access + refresh tokens (not session tokens): Don overruled Devils-Advocate; future-proof and stateless
- Hybrid categories model: Predefined global + custom per-user in single table; no per-user copy duplication
- Private data access: Admin role only for user/config management; no cross-user data visibility
- Refresh token rotation from day one: Detects token theft; adds ~30 LOC complexity but worth the security benefit
- Table recreation for users migration: Required to remove token column; SQLite cannot DROP COLUMN natively
- Mutex-locked frontend refresh: Essential to prevent random logouts with 15min token expiry
- system_config table: Avoids mixing global and per-user settings; admin-only access enforced by middleware

### Rejected Alternatives
- Session tokens with DB lookup: Don rejected — overruled Devils-Advocate; JWT preferred for stateless verification and future scalability
- Per-user category copy: Don rejected — creates duplication, no global updates possible
- Admin can see all data: Don rejected — financial data must be private
- httpOnly cookies for refresh tokens: Rejected — PWA/service worker compatibility issues; accepted localStorage with mitigations
- Soft delete for users: Don rejected — opted for hard delete with cascade

### Unresolved Objections
- localStorage XSS risk for tokens — Risk: MEDIUM — Mitigation: 15min access TTL + rotation + logout revocation
- SQLite write contention under multi-user — Risk: LOW (for expected <10 concurrent users) — Mitigation: busy_timeout=5000 + WAL mode
- Raw SQL WHERE user_id enforcement without ORM safety net — Risk: MEDIUM — Mitigation: integration tests with two users verifying isolation; code review checklist

## Acceptance Criteria

1. A new user can register (when enabled) and log in with JWT access + refresh tokens
2. Auth middleware verifies JWT without database lookup
3. Each user can only see and modify their own transactions, custom categories, and settings
4. Dashboard shows only the authenticated user's financial data
5. Changing default currency recalculates only that user's transactions
6. Refresh token rotation works: refreshing invalidates old token, issues new pair
7. Concurrent refresh attempts are deduplicated (one refresh, all requests retry)
8. Rate limiting blocks brute-force attempts on login/register endpoints
9. Admin can enable/disable registration via settings
10. Admin can create and delete users (with cascade)
11. Admin cannot see other users' transactions
12. Predefined categories appear for all users; users can add custom categories without name+type collision
13. Existing admin user data is preserved after migration
14. Existing receipt files are moved to user-scoped directories
15. All existing integration tests pass after migration
16. New integration tests verify cross-user data isolation

## Out of Scope

- Email verification / password reset via email
- OAuth / social login
- Role-based access control beyond admin/user
- Two-factor authentication
- API versioning
- Migration to PostgreSQL
- httpOnly cookie-based token storage
- Account lockout after failed login attempts (rate limiting provides partial mitigation)
- User profile editing (username/email change)
- Soft delete / account deactivation
- Audit logging of admin actions

## Open Risks

1. **Cross-user data leak via missed WHERE clause** — Risk: MEDIUM — Every raw SQL query must include user_id. Missing one leaks data. Mitigation: integration tests with two users verifying isolation per route
2. **localStorage XSS** — Risk: MEDIUM — Both tokens accessible via XSS. Mitigation: short access TTL, rotation, logout revocation. Future: migrate to httpOnly cookies
3. **SQLite concurrent writes** — Risk: LOW for <10 users — WAL mode + busy_timeout handles moderate concurrency. If the app scales beyond 10 concurrent writers, consider async SQLite or PostgreSQL
