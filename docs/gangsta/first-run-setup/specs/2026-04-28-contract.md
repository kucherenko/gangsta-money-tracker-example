# Contract: First-Run Setup Page

## Objective

Add a one-time setup page that is displayed when the application has no admin user. The page allows the user to create the initial admin account (username, password, confirm password). After creation, the user is auto-logged-in and redirected to the dashboard. This replaces the current behavior of seeding a default admin/admin user from environment variables, eliminating the insecure default credentials problem.

## Requirements

### Functional Requirements

1. **FR-001** `GET /auth/config/register` endpoint is extended to include a `needsSetup` boolean field in its response. When `needsSetup` is `true`, no admin user exists in the database. This endpoint is already unauthenticated and called on app load.

2. **FR-002** New `POST /setup` endpoint (unauthenticated) creates the initial admin user. Request body validated against `setupSchema` in `shared/schemas.ts`. Fields: `username` (3-30 chars, alphanumeric+underscore, same constraint as `registerSchema`), `password` (8-128 chars), `confirmPassword` (must match password). After inserting the admin user, `ensureSettingsRow` is called for the new user (same as register and admin-create flows). `setupSchema` reuses the username regex from `registerSchema` to prevent constraint drift.

3. **FR-003** `POST /setup` is guarded by an atomic `BEGIN IMMEDIATE` transaction that checks if any admin user exists before creating one. If any admin already exists, returns `409 Conflict` with `{ error: "Setup already completed" }`.

4. **FR-004** `POST /setup` is rate-limited to 3 requests per hour per IP address, consistent with existing rate-limiting patterns.

5. **FR-005** On successful setup, `POST /setup` returns `201 Created` with `{ token, refreshToken, user: { id, username, role } }` — matching the nested response shape of the register endpoint (`/auth/register`), enabling the frontend to use the same auto-login logic (`auth.setTokens(res.token, res.refreshToken); auth.user = res.user`).

6. **FR-006** `DELETE /admin/users/:id` is guarded to prevent deletion of the last remaining admin user. If the target is the last admin, returns `403 Forbidden` with an appropriate error message.

7. **FR-007** Frontend gains a new `#/setup` route rendering `Setup.svelte`. The setup page displays a form with username, password, and confirm password fields. On successful submission, tokens are stored in localStorage, user state is set, and the user is redirected to `#/dashboard`.

8. **FR-008** Frontend `App.svelte` checks `needsSetup` flag on mount. If `needsSetup` is `true`, the user is redirected to `#/setup` instead of `#/login`. The `#/setup` route is always directly accessible via hash navigation (bookmarkable). The auth guard in `App.svelte` must be updated to exempt `#/setup` from the redirect-to-login logic (alongside existing exemptions for `#/login` and `#/register`).

9. **FR-009** When `needsSetup` check fails due to network error, the frontend defaults to showing the login page (existing behavior). The user can manually navigate to `#/setup` if needed.

10. **FR-010** Auth state (`auth.svelte.ts`) gains a `needsSetup` reactive flag and a `checkSetupStatus()` method that calls `GET /auth/config/register` and reads the `needsSetup` field.

### Non-Functional Requirements

1. **NFR-001** The `POST /setup` endpoint must use `BEGIN IMMEDIATE` transaction for atomic check-and-create, preventing race conditions where two simultaneous requests both create admin accounts.

2. **NFR-002** Password hashing uses bcrypt (async, same as existing auth routes). Hash computation happens outside the transaction; count check, user insert, and `ensureSettingsRow` happen inside the transaction. Token generation (JWT signing, refresh token INSERT) happens after the transaction commits, outside the transaction block. The 409 "admin already exists" case is handled by the transaction function returning a discriminated result (e.g., `{ created: false }`), not by throwing inside the transaction — consistent with Constitution Commandment 3.

3. **NFR-003** No new unauthenticated reconnaissance endpoint is created. Setup status is determined via the existing `GET /auth/config/register` endpoint.

4. **NFR-004** The `POST /setup` endpoint uses raw `fetch` on the frontend (not `fetchJson` / `fetchWithAuth`) to avoid triggering 401-redirect-to-login logic in the API client.

5. **NFR-005** Token generation functions (`generateTokenPair`, `hashToken`) are extracted from `routes/auth.ts` to `backend/lib/tokens.ts` and shared between `auth.ts` and `setup.ts`, per Constitution Commandment 5 (never duplicate utility functions across route files).

6. **NFR-006** `Setup.svelte` parses error responses from `POST /setup` by reading the JSON body `{ message }` or `{ error }` fields, and displays validation errors inline on the form.

## Architectural Decisions

1. **Extend existing endpoint for setup detection** — Add `needsSetup` field to `GET /auth/config/register` rather than creating a new dedicated endpoint. Rationale: avoids creating new attack surface; the endpoint already exists and is called on app load.

2. **Admin count check for setup-needs detection** — Check `SELECT COUNT(*) FROM users WHERE role = 'admin'` to determine if setup is needed. Rationale: simplest approach; no new database columns or migrations needed. Protected against escalation by last-admin deletion guard.

3. **Remove admin env vars entirely** — `ADMIN_USERNAME` and `ADMIN_PASSWORD` are removed from all configuration (`.env.example`, `docker-compose.yml`, `validateEnv()`, `seed.ts`). Rationale: Don's decision; cleaner architecture; eliminates the insecure-default-credentials problem at its source. The password-update-on-env-change behavior in `seed.ts:29-33` is also removed as a side effect — this is documented as a breaking change.

4. **Seed function modification** — `seed()` is modified to only seed default categories and system config (`allow_registration`). Admin user creation and password synchronization from env vars are removed. `seed()` still runs on server startup (`server.ts:77`).

5. **Extract token generation to shared module** — `generateTokenPair` and `hashToken` are extracted from `routes/auth.ts` to `backend/lib/tokens.ts`, per Constitution Commandment 5. Both `auth.ts` and `setup.ts` import from the shared module.

6. **Setup creates only admin account** — No settings onboarding (currency, registration toggle). Rationale: Don's decision; settings are already configurable via the Settings page post-login; decoupling reduces scope and regression risk.

7. **Last-admin deletion guard** — `DELETE /admin/users/:id` prevents deletion when the target is the last admin. Rationale: prevents the setup endpoint from being re-opened by deleting all admins (privilege escalation vector identified in the Grilling).

8. **Minimal form: username + password + confirm password** — No email field, no settings fields. Rationale: Don's decision; email is optional in the current system and can be set later.

## Grilling Conclusions

### Key Decisions

- **Scope: Admin bootstrap ONLY**: First-run setup page creates the admin account only. No settings onboarding.
- **Detection: Extend existing endpoint**: `GET /auth/config/register` gains `needsSetup` field. No new reconnaissance endpoint.
- **Atomic guard**: `BEGIN IMMEDIATE` transaction wraps count-check and insert. Password hash computed outside transaction.
- **Last-admin deletion guard**: Prevents re-opening the setup endpoint.
- **Env vars removed**: `ADMIN_USERNAME`/`ADMIN_PASSWORD` removed entirely. Breaking change documented.
- **Seed simplified**: `seed()` retains only category and currency seeding. Admin creation removed.
- **`validateEnv()` updated**: `ADMIN_PASSWORD` removed from required production env vars.
- **Setup form minimal**: Username + password + confirm password only.
- **Auto-login on setup**: `POST /setup` returns tokens directly.
- **`#/setup` always accessible**: Direct navigation works even if automated check fails.

### Rejected Alternatives

- **Settings onboarding in setup page**: Rejected — Don decoupled settings from admin bootstrap.
- **Keep env vars as fallback**: Rejected — Don chose to remove entirely.
- **`system_config.setup_complete` flag**: Rejected — Don chose simple admin-count check.
- **CLI setup script**: Deferred — not in scope.
- **Dedicated `GET /setup/status` endpoint**: Rejected — extends existing endpoint instead.
- **Password strength enforcement beyond 8 chars**: Rejected — consistent with existing register schema.

### Unresolved Objections

1. **In-memory rate limiting is bypassable by IP spoofing** — Risk: MEDIUM — Mitigation: The self-disabling nature of the endpoint (closed after first admin) provides primary security. Rate limiting is a deterrent.
2. **Password strength for admin is only 8-char minimum** — Risk: LOW — Accepted. Consistent with existing `registerSchema`.

## Acceptance Criteria

1. Fresh application (empty database) shows the setup page on first visit — no admin/admin default credentials exist.
2. `POST /setup` successfully creates an admin user when none exists, returns auth tokens, and the user is auto-logged-in.
3. After first admin is created, `POST /setup` returns `409 Conflict` on all subsequent calls.
4. `GET /auth/config/register` returns `needsSetup: true` when no admin exists, and `needsSetup: false` when an admin exists.
5. Attempting to delete the last admin user via `DELETE /admin/users/:id` returns `403 Forbidden`.
6. Existing deployments (with existing admin in database) never see the setup page.
7. All existing backend tests pass after changes. `api.test.ts` and `multiuser.test.ts` are updated to use `POST /setup` in `beforeAll` instead of relying on `seed()` to create an admin user.
8. New backend test file covers: successful setup, duplicate setup (409), validation errors, last-admin deletion guard.
9. Frontend `#/setup` route renders setup form; on completion, redirects to `#/dashboard`.
10. Frontend redirects to `#/setup` when `needsSetup` is `true`.
11. `ADMIN_USERNAME` and `ADMIN_PASSWORD` env vars are removed from `.env.example` and `docker-compose.yml`.
12. `ADMIN_PASSWORD` is removed from `validateEnv()` required production env vars.
13. `generateTokenPair` and `hashToken` are extracted to `backend/lib/tokens.ts` and shared between `auth.ts` and `setup.ts`.
14. `setupSchema` is added to `shared/schemas.ts` with username constraints matching `registerSchema`.

## Out of Scope

- Email field on setup form
- Settings onboarding (currency selection, registration toggle) on setup page
- CLI setup script for headless deployment
- Password strength enforcement beyond existing 8-char minimum
- Email verification
- OAuth/social login
- Migration tooling for existing deployments (they keep their seeded admin)
- Multi-step wizard flow

## Open Risks

1. **Breaking change for Docker deployments** — Existing `docker-compose.yml` files referencing `ADMIN_USERNAME`/`ADMIN_PASSWORD` will need manual update. Documented in changelog.
2. **In-memory rate limiting bypassable** — Accepted. Primary security is the self-disabling endpoint.
3. **Setup endpoint is temporarily exposed** — Between app start and first admin creation, `POST /setup` is accessible. This is inherent to the problem and equivalent to the current admin/admin default risk.
